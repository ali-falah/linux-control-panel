Tradeoff: These guidelines bias toward caution over speed. For trivial tasks, use judgment.

1. Think Before Coding
Don't assume. Don't hide confusion. Surface tradeoffs.

Before implementing:

State your assumptions explicitly. If uncertain, ask.
If multiple interpretations exist, present them - don't pick silently.
If a simpler approach exists, say so. Push back when warranted.
If something is unclear, stop. Name what's confusing. Ask.
2. Simplicity First
Minimum code that solves the problem. Nothing speculative.

No features beyond what was asked.
No abstractions for single-use code.
No "flexibility" or "configurability" that wasn't requested.
No error handling for impossible scenarios.
If you write 200 lines and it could be 50, rewrite it.
Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

3. Surgical Changes
Touch only what you must. Clean up only your own mess.

When editing existing code:

Don't "improve" adjacent code, comments, or formatting.
Don't refactor things that aren't broken.
Match existing style, even if you'd do it differently.
If you notice unrelated dead code, mention it - don't delete it.
When your changes create orphans:

Remove imports/variables/functions that YOUR changes made unused.
Don't remove pre-existing dead code unless asked.
The test: Every changed line should trace directly to the user's request.

4. Goal-Driven Execution
Define success criteria. Loop until verified.

Transform tasks into verifiable goals:

"Add validation" → "Write tests for invalid inputs, then make them pass"
"Fix the bug" → "Write a test that reproduces it, then make it pass"
"Refactor X" → "Ensure tests pass before and after"
For multi-step tasks, state a brief plan:

1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

Also Super Important : UI/UX must match system design ,use always already built in components ( inputs , buttons ... etc ) , Use best practice code strategy and type do not do a redundant coding 

5. Build Policy:
Do NOT run full production builds (`npm run build`) after every change — it takes too long. Rely on targeted syntax/type checks, tests, and the active dev server HMR unless explicitly requested by the user.

6. Report Observed Bugs — Let the User Decide
While working you will inevitably stumble on bugs that are NOT part of the current request
(broken CSS class names, missing store members, non-existent classes, dead code, inconsistent
component usage, etc.).

Do NOT silently fix them and do NOT expand the task to cover them.
Collect them and report them to the user, each with:
- Where it is (file:line)
- The ROOT CAUSE, not just the symptom
- The one-line proposed fix
Then stop and let the user review and choose what to fix.

Sweeping the whole codebase for the same bug class counts as a separate task — do it only when
the user asks for it or explicitly says "fix all broken issues". Otherwise report first.

Examples of the class of bug worth reporting (not fixing unasked):
- `class="btn ... -outline"` — variant classes only exist via the `variant` prop, so a
  hand-written `-outline` silently falls back to the unstyled base class
- `class="badge badge-danger"` — the real variants are success/error/warning/info/muted/outline
- `uiStore.someMethod()` where the store has no such member → runtime TypeError
- Svelte compiler warnings (a11y_*, css_unused_selector, state_referenced_locally)
 
IMPORTANT — SINGLE SOURCE OF TRUTH RULE (enforce before writing any code):

Before implementing anything, scan the codebase for:
- Existing CSS classes, design tokens, or style patterns that already cover what you need — reuse them, never duplicate.
- Existing utility functions, helpers, or modules with similar functionality — extend or call them, never rewrite.
- Existing validators, constants, or type definitions already in root_policy.rs, privilege.rs, or any shared module — import and reuse, never copy inline.
- Existing error-message strings or response-shape patterns already in use — match them exactly for consistency.

If you find an existing thing that covers the need: USE IT. Do not create a new one alongside it.
If you find something that almost covers the need: EXTEND IT (with minimal change, following existing naming and style). Do not duplicate it.
If nothing exists: CREATE IT once, in the right shared location, so future code can reuse it.

NEVER:
- Define the same constant, validator, CSS class, or function in two places.
- Reimplement logic that already exists elsewhere, even if it seems simpler to inline it.
- Create a new helper when an existing one could be extended by one parameter.
- Copy-paste code blocks between files; extract to a shared module instead.

Before writing each function, type, constant, or style rule: search first. If found, reuse. If not found, place it where it can be reused by future code.

This applies to: Rust code, Svelte components, CSS/styles, TypeScript utilities, test helpers, fixture setup code, error messages, and argv/command shapes.
